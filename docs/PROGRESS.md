- 2026-07-04 — **Fixed auth-bypass**: `evaluate_hello`'s `NeedsApproval` verdict didn't distinguish a verified pairing proof from no proof at all, so `handle_hello` (the headless helper the default CLI host uses, since it runs with no approval UI / `approval_tx: None`) auto-enrolled *any* LAN client sending `Hello{pair_proof: None}` — no token check. `HelloVerdict::NeedsApproval` now carries `proof_verified: bool`; `handle_hello` rejects `proof_verified: false` instead of committing it. See `crates/net/src/enroll.rs`, `crates/host/src/server.rs`, `docs/PROTOCOL.md` §Identity & transport security.
- 2026-07-04 — **RFI (Reference-Frame-Invalidation) loss recovery** implemented end-to-end: `ClientMsg::InvalidateRefFrames { first_frame, last_frame }` (`crates/proto/src/control.rs`, `docs/PROTOCOL.md`); `FrameReassembler::take_loss_report()` (`crates/core/src/reassemble.rs`) replaces the dead `idr_requested` flag with a real `LossReport::{Invalidate, NeedIdr}` decision (const `REF_WINDOW: u16 = 32` — a generous, unmeasured guess at encoder reference-window depth, revisit once M2 lands); `VideoEncoder::invalidate_ref_frames` (`crates/host/src/encode.rs`) defaults to `force_idr()` so every encoder recovers today, just not surgically; `crates/host/src/server.rs` wires the control loop (`InvalidateRefFrames` rate-limited to 1/60ms vs `RequestIdr`'s 1/250ms) and `stream_video`. Real hardware invalidation (NVENC `NvEncInvalidateRefFrames`, AMF/QSV) stays a `// TODO(M2)` behind the trait in `crates/host/src/capture.rs`, which also needs a frame_id↔encoder-reference-index map that doesn't exist yet. Along the way, fixed two latent `FrameReassembler` bugs surfaced by actually acting on loss reports (previously harmless since nothing consumed them): a late redundant FEC shard for an already-completed frame_id could create a phantom bucket later mis-reported as a loss, and the loss-reference gap computation could go negative when later frames complete out of order before a stale one is evicted. `crates/devtools/src/devclient.rs` and `app/rust/src/android/play.rs` both send `InvalidateRefFrames`/`RequestIdr` off the new report now.
- 2026-07-04 — **Legacy Win32 tray removed**: `crates/host/src/tray.rs`, the `--legacy-tray`/`--headless` CLI flags, and the now-unused `windows-sys` Gdi/Shell/DataExchange/LibraryLoader/Memory/Threading features are gone. The Flutter desktop app (`app/`) is the only Windows host UI now; `streambeam-host.exe` always runs headless (`run-host.bat` updated to match — no more flag needed, and no more identical-to-a-crash confusion since that was always the plan once the Flutter tray-click-to-show landed).
- 2026-07-04 — **Android decoder low-latency mode**: `app/rust/src/android/play.rs`'s `try_configure_decoder` now sets `MediaFormat` key `"low-latency"` (`MediaFormat.KEY_LOW_LATENCY`, API 30+, harmlessly ignored below that). Without it, some vendor decoders default to a throughput-oriented pipeline buffering several frames before any output; if that decode rate falls behind the host's real-time ~30fps feed, the input buffer pool exhausts and `feed_sample()` hard-errors the whole session (not just one frame) — a plausible root cause for reports of the phone being stuck at ~2fps despite the host log showing a healthy ~28fps encode. Matches Moonlight's Android client, which sets this for the same reason. Not yet verified on a real device from this machine (no phone attached here) — needs a rebuild + on-phone test.
- 2026-07-04 — **Decision: move host encode off the CPU ("GPU everything")**. Today `crates/host/src/capture.rs` hardcodes the *software* Media Foundation H.264 MFT (`CLSID_CMSH264ENCODER`) and drives it synchronously — deliberate at the time to sidestep async-MFT/COM complexity, but it caps encode throughput on the CPU and is the likely ceiling behind the ~10-30fps host-side numbers seen throughout the M2 debugging arc. Plan: **Stage 1** — enumerate hardware H.264 encoder MFTs via `MFTEnumEx(MFT_CATEGORY_VIDEO_ENCODER, MFT_ENUM_FLAG_HARDWARE, ...)`, falling back to the existing software CLSID when none is found (e.g. no GPU / driver doesn't register one); since Windows requires hardware MFTs to implement the *async* MFT contract, this also means moving `encode()`/`drain_output()` off eager synchronous `ProcessInput`/`ProcessOutput` onto the event-driven model (`MF_TRANSFORM_ASYNC_UNLOCK`, `IMFMediaEventGenerator::GetEvent`, `METransformNeedInput`/`METransformHaveOutput`). Still CPU-fed NV12 samples at this stage. **Stage 2** — true zero-copy: GPU-side BGRA→NV12 + downscale (`ID3D11VideoProcessor` or a hand-written compute shader, matching Sunshine's approach) feeding the encoder D3D11-backed samples via `IMFDXGIDeviceManager`/`MFCreateDXGISurfaceBuffer`, so the CPU never touches a captured frame's pixels at all.
- 2026-07-05 — **Pivoted off Media Foundation's hardware-MFT path entirely, to direct NVENC.** Stage 1 above (generic hardware MFT wrapper around NVENC via `MFTEnumEx`) got real hardware frames flowing, but hit a confirmed, unrecoverable intermittent freeze after a variable number of frames (30–270), reproduced three separate times; a live `procdump`+`cdb` stack trace showed the capture thread parked on a normal wait, not stuck inside any MF/driver call — genuinely lost, not just slow. Checked how Sunshine and RustDesk actually do this on Windows: **neither goes through Media Foundation's hardware MFT wrapper for NVIDIA.** New `crates/host/src/nvenc.rs`: hand-rolled minimal bindings to the raw NVENC SDK (`nvEncodeAPI64.dll` via `NvEncodeAPICreateInstance`), following Sunshine's pattern — one `ID3D11Texture2D` registered once via `NvEncRegisterResource`, one process-wide completion event, `WaitForSingleObject(event, 100ms)` per frame that drops the frame on timeout rather than blocking (the reliability property MF's async contract lacked). `crates/host/src/capture.rs`'s `Pipeline` now tries NVENC first, falling back to the Media Foundation *software* encoder (sync contract, none of the async failure modes) when no NVIDIA GPU is present. Struct/enum/GUID layouts cross-checked field-by-field against the authoritative FFmpeg `nv-codec-headers/nvEncodeAPI.h` (not the initial secondhand reference crate, which had several — see below).
- 2026-07-05 — **NVENC struct-layout bugs found via real end-to-end testing, not just compiling clean.** A wrong-sized field (`max_me_hint_counts_per_block`/`me_hint_counts_per_block`: `[u32;4]` instead of `[u32;8]`, since `NVENC_EXTERNAL_ME_HINT_COUNTS_PER_BLOCKTYPE` is itself 4 u32s and there are 2 of them) silently misaligned every field after it in `NV_ENC_INITIALIZE_PARAMS` and `NV_ENC_PIC_PARAMS`, breaking `NvEncInitializeEncoder`. A field-order swap in `NV_ENC_LOCK_BITSTREAM` meant the code was reading the *input* handle field as the *output* bitstream data pointer. `NV_ENC_CREATE_BITSTREAM_BUFFER` was missing two leading fields entirely. All three were invisible to `cargo check`/`cargo build` (matching field *types*, wrong field *order/count* — classic FFI layout risk) and were only caught by capturing real encoder output and decoding it with `ffmpeg` independent of our own code.
- 2026-07-05 — **`NV_ENC_PIC_FLAG_FORCEIDR` bug + workaround.** Had it as `0x1` (checked against a secondhand reference crate) instead of the real value `0x2` — `0x1` is actually `NV_ENC_PIC_FLAG_FORCEINTRA` (an all-intra frame, but *not* a real IDR: no SPS/PPS repeat, no NAL type 5, doesn't reset the decoder's reference chain). Every "forced keyframe" after the session's very first frame (which NVENC always makes a real IDR automatically, independent of any flag) was silently just a large all-intra P-slice. Invisible on a lossless network (nothing ever needed resyncing); catastrophic on real lossy WiFi, since no genuine recovery point ever existed past frame 0 — this was the actual root cause behind a long "0fps / black screen / stuck on one frame" investigation. Fixed the flag, but empirically **the driver still doesn't honor it** even with the correct value — almost certainly the UltraLowLatency preset's codec-specific `idrPeriod` (a field inside the opaque per-codec config union we deliberately don't model) defaulting to "never auto-insert" and also swallowing explicit force requests. Rather than reach further into that union (real risk of repeating the struct-layout class of bug above), `crates/host/src/capture.rs::encode()` now recreates the whole NVENC session on a force-IDR request instead — a brand new session's first frame is always a real IDR, the one mechanism already proven 100% reliable. Not yet confirmed fixed on a real device (session paused mid-verification); worth a cheaper fix later if the codec-specific `idrPeriod` field turns out safe to model.
- 2026-07-05 — **GPU downscale: two failed attempts before landing on Sunshine's actual approach.** Capture and encode resolution differ whenever native resolution exceeds the FEC shard-count limit (e.g. any 4K display). First cut used a CPU round-trip (map → nearest-neighbor resize → upload) for this — labeled "rare" in a comment that was wrong for any 4K user, and the dominant per-frame cost once measured (avg capture time climbing from 5ms to 80ms+ over a session, with growing frame-acquire timeouts). Second cut replaced it with `ID3D11VideoContext::VideoProcessorBlt` (the Windows "video processor" API) — worked, but failed intermittently with `E_INVALIDARG` on `CreateVideoProcessorInputView`, silently dropping frames. Landed on what Sunshine actually does: a hand-written pixel-shader pass (`crates/host/src/scale.rs`) — a full-screen triangle generated in the vertex shader from `SV_VertexID` (no vertex buffer needed) samples the captured frame with a bilinear sampler into a render target sized to the encode resolution; compiled at runtime via `D3DCompile` (`d3dcompiler_47.dll`, ships with Windows). Ordinary D3D11 render-to-texture, not a specialized video API, so it doesn't inherit the Video Processor API's known cross-vendor/driver inconsistency. Verified via a 900-frame/30s soak: capture time flat at ~0ms for the whole run, zero errors, vs. the CPU path's climb and the Video Processor path's intermittent failures.
- 2026-07-05 — **Client-side Android decode backpressure fix** (`app/rust/src/android/play.rs`). Found via real-device logcat (wireless `adb`) that the client's receive queue was permanently pinned at its 64-datagram safety-valve cap from the first frame onward — MediaCodec's `dequeue_input_buffer`/`dequeue_output_buffer` calls used a 30ms timeout on the *same thread* driving the network read loop; every "not ready yet" dequeue burned the full 30ms, capping the loop below real-time and guaranteeing a permanent backlog once even slightly behind. Dropped the timeout to 2ms (with a bounded retry in `feed_sample` so "not ready *yet*" isn't treated as a hard error at the new tighter timeout) and collapsed the greedy-drain loop's per-datagram `runtime.block_on` calls (up to 64/iteration) into one `block_on` per outer iteration — the per-datagram version added real, measurable overhead entering the async runtime thousands of times a second, showing up as sustained high CPU use. Also stopped feeding a lone P-frame per batch while catching up (its reference chain was already broken by the frames skipped ahead of it — MediaCodec "successfully" decodes that into corrupted output rather than erroring, indistinguishable from a black screen); now skips *every* non-keyframe while behind and waits for a real keyframe to resync.
- 2026-07-05 — **Fixed a real, 100%-reproducible race between successive `stream_video` sessions on the same shared encoder** (`crates/host/src/server.rs`), found chasing what looked like a client-only bug but reproduced identically against the `MockEncoder` test harness (`known_client_reconnect_without_qr`, previously failing on clean `main` too — confirmed via `git stash` before attributing it to today's changes). The shared encoder (Desktop Duplication / a single `MockEncoder` in tests is single-instance) only supports one real viewer at a time; a new session's `enc.force_idr()` and its first `enc.encode_next()` are two *separate* lock acquisitions, not one atomic step, so a still-live previous session's loop could call `encode_next()` in between and advance the shared position right back out from under the new session's first frame. `HostControls::start_streaming` now closes the previous connection *and awaits its `stream_video` task's `JoinHandle` to fully exit* before returning, so the handoff is synchronous, not eventually-consistent; `stream_video` also gets an immediate in-memory `is_active_stream` check (doesn't wait on the QUIC close handshake `conn.close_reason()` depends on). Fixes the flaky-looking reconnect test as a side effect of a genuine correctness fix, not a test-only workaround.
- 2026-07-05 — **Extracted the single-active-viewer handoff into `crates/host/src/active_stream.rs`** (`ActiveStreamTracker<C>`, generic over a minimal `CloseableConn` trait implemented for `quinn::Connection`) purely so the concurrency logic above — the actual thing worth guarding against regression — gets a fast, in-process unit test (`tests::superseding_waits_for_old_task_to_finish`) instead of only the slow, subprocess-spawning `known_client_reconnect_without_qr` integration test.
