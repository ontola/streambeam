- 2026-08-18 — **The service updates its own worker now, because the friction was the bug.** Deploying a new `streambeam-host.exe` meant an elevated stop/copy/start: the worker runs as SYSTEM, Windows locks a running image against overwrite, and a non-admin can't stop a service to release it. - 2026-07-05 — **`NV_ENC_PIC_FLAG_FORCEIDR` bug + workaround.** Had it as `0x1` (checked against a secondhand reference crate) instead of the real value `0x2` — `0x1` is actually `NV_ENC_PIC_FLAG_FORCEINTRA` (an all-intra frame, but *not* a real IDR: no SPS/PPS repeat, no NAL type 5, doesn't reset the decoder's reference chain). - 2026-07-05 — **GPU downscale: two failed attempts before landing on Sunshine's actual approach.** Capture and encode resolution differ whenever native resolution exceeds the FEC shard-count limit (e.g. any 4K display). - 2026-07-05 — **Client-side Android decode backpressure fix** (`app/rust/src/android/play.rs`). Found via real-device logcat (wireless `adb`) that the client's receive queue was permanently pinned at its 64-datagram safety-valve cap from the first frame onward — MediaCodec's `dequeue_input_buffer`/`dequeue_output_buffer` calls used a 30ms timeout on the *same thread* driving the network read loop; every "not ready yet" dequeue burned the full 30ms, capping the loop below real-time and guaranteeing a permanent backlog once even slightly behind. Dropped the timeout to 2ms (with a bounded retry in `feed_sample` so "not ready *yet*" isn't treated as a hard error at the new tighter timeout) and collapsed the greedy-drain loop's per-datagram `runtime.block_on` calls (up to 64/iteration) into one `block_on` per outer iteration — the per-datagram version added real, measurable overhead entering the async runtime thousands of times a second, showing up as sustained high CPU use.
