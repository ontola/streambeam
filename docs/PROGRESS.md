- 2026-07-04 — **Android decoder low-latency mode**: `app/rust/src/android/play.rs`'s `try_configure_decoder` now sets `MediaFormat` key `"low-latency"` (`MediaFormat.KEY_LOW_LATENCY`, API 30+, harmlessly ignored below that). Without it, some vendor decoders default to a throughput-oriented pipeline buffering several frames before any output; if that decode rate falls behind the host's real-time ~30fps feed, the input buffer pool exhausts and `feed_sample()` hard-errors the whole session (not just one frame) — a plausible root cause for reports of the phone being stuck at ~2fps despite the host log showing a healthy ~28fps encode. Matches Moonlight's Android client, which sets this for the same reason. Not yet verified on a real device from this machine (no phone attached here) — needs a rebuild + on-phone test.
- 2026-07-04 — **Decision: move host encode off the CPU ("GPU everything")**. Today `crates/host/src/capture.rs` hardcodes the *software* Media Foundation H.264 MFT (`CLSID_CMSH264ENCODER`) and drives it synchronously — deliberate at the time to sidestep async-MFT/COM complexity, but it caps encode throughput on the CPU and is the likely ceiling behind the ~10-30fps host-side numbers seen throughout the M2 debugging arc. Plan: **Stage 1** — enumerate hardware H.264 encoder MFTs via `MFTEnumEx(MFT_CATEGORY_VIDEO_ENCODER, MFT_ENUM_FLAG_HARDWARE, ...)`, falling back to the existing software CLSID when none is found (e.g. no GPU / driver doesn't register one); since Windows requires hardware MFTs to implement the *async* MFT contract, this also means moving `encode()`/`drain_output()` off eager synchronous `ProcessInput`/`ProcessOutput` onto the event-driven model (`MF_TRANSFORM_ASYNC_UNLOCK`, `IMFMediaEventGenerator::GetEvent`, `METransformNeedInput`/`METransformHaveOutput`). Still CPU-fed NV12 samples at this stage. **Stage 2** — true zero-copy: GPU-side BGRA→NV12 + downscale (`ID3D11VideoProcessor` or a hand-written compute shader, matching Sunshine's approach) feeding the encoder D3D11-backed samples via `IMFDXGIDeviceManager`/`MFCreateDXGISurfaceBuffer`, so the CPU never touches a captured frame's pixels at all.
- 2026-07-05 — **Pivoted off Media Foundation's hardware-MFT path entirely, to direct NVENC.** Stage 1 above (generic hardware MFT wrapper around NVENC via `MFTEnumEx`) got real hardware frames flowing, but hit a confirmed, unrecoverable intermittent freeze after a variable number of frames (30–270), reproduced three separate times; a live `procdump`+`cdb` stack trace showed the capture thread parked on a normal wait, not stuck inside any MF/driver call — genuinely lost, not just slow. Checked how Sunshine and RustDesk actually do this on Windows: **neither goes through Media Foundation's hardware MFT wrapper for NVIDIA.** New `crates/host/src/nvenc.rs`: hand-rolled minimal bindings to the raw NVENC SDK (`nvEncodeAPI64.dll` via `NvEncodeAPICreateInstance`), following Sunshine's pattern — one `ID3D11Texture2D` registered once via `NvEncRegisterResource`, one process-wide completion event, `WaitForSingleObject(event, 100ms)` per frame that drops the frame on timeout rather than blocking (the reliability property MF's async contract lacked). `crates/host/src/capture.rs`'s `Pipeline` now tries NVENC first, falling back to the Media Foundation *software* encoder (sync contract, none of the async failure modes) when no NVIDIA GPU is present. Struct/enum/GUID layouts cross-checked field-by-field against the authoritative FFmpeg `nv-codec-headers/nvEncodeAPI.h` (not the initial secondhand reference crate, which had several — see below).
- 2026-07-05 — **NVENC struct-layout bugs found via real end-to-end testing, not just compiling clean.** A wrong-sized field (`max_me_hint_counts_per_block`/`me_hint_counts_per_block`: `[u32;4]` instead of `[u32;8]`, since `NVENC_EXTERNAL_ME_HINT_COUNTS_PER_BLOCKTYPE` is itself 4 u32s and there are 2 of them) silently misaligned every field after it in `NV_ENC_INITIALIZE_PARAMS` and `NV_ENC_PIC_PARAMS`, breaking `NvEncInitializeEncoder`. A field-order swap in `NV_ENC_LOCK_BITSTREAM` meant the code was reading the *input* handle field as the *output* bitstream data pointer. `NV_ENC_CREATE_BITSTREAM_BUFFER` was missing two leading fields entirely. All three were invisible to `cargo check`/`cargo build` (matching field *types*, wrong field *order/count* — classic FFI layout risk) and were only caught by capturing real encoder output and decoding it with `ffmpeg` independent of our own code.
- 2026-07-05 — **`NV_ENC_PIC_FLAG_FORCEIDR` bug + workaround.** Had it as `0x1` (checked against a secondhand reference crate) instead of the real value `0x2` — `0x1` is actually `NV_ENC_PIC_FLAG_FORCEINTRA` (an all-intra frame, but *not* a real IDR: no SPS/PPS repeat, no NAL type 5, doesn't reset the decoder's reference chain). Every "forced keyframe" after the session's very first frame (which NVENC always makes a real IDR automatically, independent of any flag) was silently just a large all-intra P-slice. Invisible on a lossless network (nothing ever needed resyncing); catastrophic on real lossy WiFi, since no genuine recovery point ever existed past frame 0 — this was the actual root cause behind a long "0fps / black screen / stuck on one frame" investigation. Fixed the flag, but empirically **the driver still doesn't honor it** even with the correct value — almost certainly the UltraLowLatency preset's codec-specific `idrPeriod` (a field inside the opaque per-codec config union we deliberately don't model) defaulting to "never auto-insert" and also swallowing explicit force requests. Rather than reach further into that union (real risk of repeating the struct-layout class of bug above), `crates/host/src/capture.rs::encode()` now recreates the whole NVENC session on a force-IDR request instead — a brand new session's first frame is always a real IDR, the one mechanism already proven 100% reliable. Not yet confirmed fixed on a real device (session paused mid-verification); worth a cheaper fix later if the codec-specific `idrPeriod` field turns out safe to model.
- 2026-07-05 — **GPU downscale: two failed attempts before landing on Sunshine's actual approach.** Capture and encode resolution differ whenever native resolution exceeds the FEC shard-count limit (e.g. any 4K display). First cut used a CPU round-trip (map → nearest-neighbor resize → upload) for this — labeled "rare" in a comment that was wrong for any 4K user, and the dominant per-frame cost once measured (avg capture time climbing from 5ms to 80ms+ over a session, with growing frame-acquire timeouts). Second cut replaced it with `ID3D11VideoContext::VideoProcessorBlt` (the Windows "video processor" API) — worked, but failed intermittently with `E_INVALIDARG` on `CreateVideoProcessorInputView`, silently dropping frames. Landed on what Sunshine actually does: a hand-written pixel-shader pass (`crates/host/src/scale.rs`) — a full-screen triangle generated in the vertex shader from `SV_VertexID` (no vertex buffer needed) samples the captured frame with a bilinear sampler into a render target sized to the encode resolution; compiled at runtime via `D3DCompile` (`d3dcompiler_47.dll`, ships with Windows). Ordinary D3D11 render-to-texture, not a specialized video API, so it doesn't inherit the Video Processor API's known cross-vendor/driver inconsistency. Verified via a 900-frame/30s soak: capture time flat at ~0ms for the whole run, zero errors, vs. the CPU path's climb and the Video Processor path's intermittent failures.
- 2026-07-05 — **Client-side Android decode backpressure fix** (`app/rust/src/android/play.rs`). Found via real-device logcat (wireless `adb`) that the client's receive queue was permanently pinned at its 64-datagram safety-valve cap from the first frame onward — MediaCodec's `dequeue_input_buffer`/`dequeue_output_buffer` calls used a 30ms timeout on the *same thread* driving the network read loop; every "not ready yet" dequeue burned the full 30ms, capping the loop below real-time and guaranteeing a permanent backlog once even slightly behind. Dropped the timeout to 2ms (with a bounded retry in `feed_sample` so "not ready *yet*" isn't treated as a hard error at the new tighter timeout) and collapsed the greedy-drain loop's per-datagram `runtime.block_on` calls (up to 64/iteration) into one `block_on` per outer iteration — the per-datagram version added real, measurable overhead entering the async runtime thousands of times a second, showing up as sustained high CPU use. Also stopped feeding a lone P-frame per batch while catching up (its reference chain was already broken by the frames skipped ahead of it — MediaCodec "successfully" decodes that into corrupted output rather than erroring, indistinguishable from a black screen); now skips *every* non-keyframe while behind and waits for a real keyframe to resync.
- 2026-07-05 — **Fixed a real, 100%-reproducible race between successive `stream_video` sessions on the same shared encoder** (`crates/host/src/server.rs`), found chasing what looked like a client-only bug but reproduced identically against the `MockEncoder` test harness (`known_client_reconnect_without_qr`, previously failing on clean `main` too — confirmed via `git stash` before attributing it to today's changes). The shared encoder (Desktop Duplication / a single `MockEncoder` in tests is single-instance) only supports one real viewer at a time; a new session's `enc.force_idr()` and its first `enc.encode_next()` are two *separate* lock acquisitions, not one atomic step, so a still-live previous session's loop could call `encode_next()` in between and advance the shared position right back out from under the new session's first frame. `HostControls::start_streaming` now closes the previous connection *and awaits its `stream_video` task's `JoinHandle` to fully exit* before returning, so the handoff is synchronous, not eventually-consistent; `stream_video` also gets an immediate in-memory `is_active_stream` check (doesn't wait on the QUIC close handshake `conn.close_reason()` depends on). Fixes the flaky-looking reconnect test as a side effect of a genuine correctness fix, not a test-only workaround.

- 2026-07-05 — **Root-caused "stuck on frame 1" as a client-side bug, not a host/encode bug.** Real-device testing (wireless `adb`, host log cross-referenced against phone logcat) showed the host streaming valid H.264 continuously at ~15-29fps for entire sessions while the phone displayed nothing past the first keyframe. `app/rust/src/android/play.rs`'s "am I falling behind real-time" check was `batch.len() > 1` — counting raw QUIC datagrams read in one poll iteration. But every access unit is FEC-sharded into ≤1200-byte pieces (`MAX_SHARD_PAYLOAD`, `crates/proto/src/media.rs`), so any real frame (routinely 5-70KB) is a dozen-plus datagrams that legitimately arrive back-to-back on a LAN — `behind` was therefore *almost always true*, and the "skip every non-keyframe while behind" recovery logic (itself correct, added for a different reason — see above) ate essentially every P-frame forever after the initial IDR. Fixed by computing `behind` from the count of *completed reassembled frames* per batch instead of raw datagram count — multiple full frames finishing in one poll iteration is a real backlog signal; multiple shards of one frame is not. First real-device test after the fix showed actual moving video (0-20fps, ~400kbps) for the first time all session — bitrate/fps tuning still needed but the fundamental pipe is now open.
- 2026-07-05 — **Added a global panic hook** (`crates/host/src/logging::install_panic_hook`, wired in both `crates/host/src/main.rs` and `app/rust/src/api/mod.rs::init_app` behind the same `cfg(any(windows, target_os = "android"))` gate `mod host` already uses). Motivated by a live repro: host log showed a session sending clean frames at ~15-22fps for 16.7s straight, then nothing — no error, no more "capture stats" lines, connection only closing 14.5s later once the client's own 5s read-timeout gave up. No Windows TDR event, no crash event, process still `Responding: True` afterward — consistent with a panic on a detached background thread (capture/encode runs on its own `std::thread`, not the async runtime) unwinding silently, since release builds are `windows_subsystem = "windows"` (no console) and nothing was routing panics into `host.log`. Next occurrence will at least leave a trace.
- 2026-07-05 — **Made desktop-capture + NVENC session startup lazy** (`crates/host/src/server.rs::run`): previously built unconditionally at host launch via `build_encoder()`, holding a live DXGI Desktop Duplication interface and NVENC session open for the process's entire lifetime regardless of whether any client ever connected. Reported symptom: audible GPU/HDMI-audio hiccups on the host machine with zero active listeners. Deferred via `Arc<tokio::sync::OnceCell<...>>`, built on the first real connection instead (`encoder_cell.get_or_init(...)` inside the accept loop) — nothing capture/GPU-related runs until a viewer actually shows up. Teardown-on-last-disconnect (releasing the GPU resources again once nobody's watching) is a follow-up, not done here — the immediate complaint was specifically "hiccups with no listeners since launch," which lazy startup fully addresses on its own.
- 2026-07-06 — **Fixed the shared encoder never honoring a resolution/fps change after the first-ever connection.** `encoder_cell` was a `tokio::sync::OnceCell` — built once from whichever client's `SessionRequest` happened to connect first, then permanently reused for every later connection regardless of what it asked for. Surfaced as the new client-side `StreamMode`/Custom-resolution picker (`app/lib/stream_player.dart`) silently doing nothing: reconnecting with a lower `resolutionScale` still got the original session's encoder untouched. `encoder_cell` is now a `tokio::sync::Mutex<Option<CachedEncoder>>` (`crates/host/src/server.rs`) that remembers the `(build_fps, build_dim)` it was built for and rebuilds when a new `SessionRequest` asks for different caps. Rebuild only happens after `controls.start_streaming(...)` has already waited for any previous connection's `stream_video` task to fully exit (see `ActiveStreamTracker`), so it can never race a still-running encoder consumer. Doesn't handle a client re-sending `SessionRequest` mid-connection without reconnecting (the already-spawned `stream_video` task would keep the old encoder Arc) — not a real scenario today, since every client here reconnects fully to change caps.
- 2026-07-07 — **Root-caused visible capture artifacts/flashing to HDR desktops.** `crates/host/src/capture.rs`'s `create_duplication` used plain `IDXGIOutput1::DuplicateOutput`, which hands back frames in whatever format the desktop is actually composited in — confirmed via a new diagnostic log (`IDXGIOutput6::GetDesc1`) that the test machine's display was running `DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020` (HDR10/PQ, 10-bit). `create_staging`'s `CopyResource` target has always assumed 8-bit `DXGI_FORMAT_B8G8R8A8_UNORM`, so on an HDR desktop the real frame (16-bit-per-channel float/scRGB) was being misread through an 8-bit lens — exactly the kind of stride/format mismatch that produces garbled, motion-triggered artifacts. Fixed by switching to `IDXGIOutput5::DuplicateOutput1(device, 0, &[DXGI_FORMAT_B8G8R8A8_UNORM])`, which explicitly requests the SDR format and lets Windows do the HDR→SDR tone-mapping itself, rather than us reading whatever format came back unchecked. Needed a new `Win32_Graphics_Gdi` Cargo feature (required by `IDXGIOutput6::GetDesc1`/`IDXGIOutput5::DuplicateOutput1`'s cfg gates in the `windows` crate).
- 2026-07-07 — **Root-caused "fps very inconsistent" / "data rate collapses" to runaway NVENC session recreation, not a capacity problem.** `crates/host/src/capture.rs` has no live `NvEncReconfigureEncoder` path yet (documented TODO) — both a bitrate change *and* `force_idr()` are implemented as a full NVENC session teardown+rebuild, which is expensive and itself briefly disrupts the stream. Two things were feeding that recreate far more often than intended: (1) `VideoEncoder::invalidate_ref_frames`'s default (what NVENC uses, since real RFI invalidation is still a TODO) falls straight through to `force_idr()` — costing exactly as much as a full `RequestIdr` — but `InvalidateRefFrames` in `crates/host/src/server.rs` was gated at only 60ms vs `RequestIdr`'s 250ms, on the stale assumption (from RFI's original design intent) that invalidation would be cheap; (2) `stream_video`'s `MIN_RECREATE_INTERVAL` (bitrate-triggered recreates) was only 800ms, which combined with the adaptive controller's own 10%-every-5-clean-windows ease-up ratchet meant a recreate could land almost every single ~1s report window. Net effect, visible in `host.log`: recreate → brief stall/burst → looks like fresh loss/congestion next window → another backoff → another recreate, an almost-continuous cycle that capped fps well below the client's requested 60fps and made bitrate sawtooth. Fixed by gating `InvalidateRefFrames` at 250ms (matching `RequestIdr`, since it costs the same today) and raising `MIN_RECREATE_INTERVAL` to 4s. A real `NvEncReconfigureEncoder` binding (avoiding a session rebuild for bitrate changes entirely) is the proper fix but needs the full authoritative NVENC SDK header to get the struct layout right — this repo has already hit three separate struct-layout bugs (see 2026-07-05 entries) from doing that without one; deferred rather than risk a fourth blind.
- 2026-07-07 — **Second pass at the NVENC-recreate churn: widened both sides further after the first gate wasn't enough.** Even after gating `InvalidateRefFrames` at 250ms and `MIN_RECREATE_INTERVAL` at 4s (see above), real-device testing still showed `RequestIdr`/`InvalidateRefFrames` every 2-4s with the host reporting zero real packet loss/congestion. Root cause was client-side: `app/rust/src/android/play.rs`'s `behind = completions.len() > 1` (a batch of the receive loop reassembling more than one complete frame at once) is common, healthy jitter on a fast LAN at up to 60fps — and especially common right after a host-side session recreate's own brief stall flushes a small burst once it resumes. Treating that as "falling behind" and requesting resync after only `IDR_RESYNC_THRESHOLD = 8` accumulated skips was self-sustaining: recreate → burst → mistaken-for-backlog → resync request → another recreate. Raised `behind`'s threshold to `> 5` and `IDR_RESYNC_THRESHOLD` to 40, and separately widened the host's bitrate ease-up ratchet from 5 to 15 clean windows before nudging up (so an already-healthy connection isn't recreating the encoder just to creep toward a ceiling it doesn't need). A real backlog still hits even these higher thresholds within a couple of seconds; this just stops short bursts from mistakenly counting.
- 2026-07-07 — **Root-caused the "connect a device, chrome disappears, nothing happens — second tap works" bug** to a widget-tree reparenting issue, not a race or a native crash (confirmed via targeted `debugPrint` tracing with object `hashCode`, since generic logcat capture kept missing the moment across several attempts). Tapping a device flips the global `appImmersive` `ValueNotifier` to `true` as the very first step of `_beginSession` (`main.dart`) — and in `AppShell` (`beam_page.dart`), that used to make the landscape-phone branch return a *differently shaped* tree (dropping the `Row`/`NavigationRail` wrapper around the `IndexedStack` holding `WatchPage`/`BeamPage`). Flutter can't reconcile a widget moving to a different parent/depth between rebuilds, so it destroyed and rebuilt `WatchPage`'s whole `State` — silently abandoning the connection attempt that same `setState` call had just started, with all fields (`_busy`, `_showVideo`, `_sessionId`) reset back to their initial values and no error, since the old State object simply ceased to exist mid-call. The second tap "worked" only because `appImmersive` was already `true` by then, so `AppShell` didn't rebuild (and reparent) at all. Fixed by always building the same `Scaffold > SafeArea > Row > Expanded(content) [+ optional NavigationRail]` shape regardless of `immersive`/orientation, toggling only which pieces are *visible* — `content` now stays at one stable tree position no matter what.
- 2026-07-05 — **Replaced per-poll mDNS browsing with a persistent `Browser`** (`crates/net/src/discovery.rs`). The Android app's `discover_hosts` FRB call (polled every 8s from `main.dart`) previously called `streambeam_net::browse()`, which creates a brand-new `mdns_sd::ServiceDaemon` from scratch every single call — no warm cache, no state carried between polls. Since mDNS responders intentionally jitter their reply timing (RFC 6762), a response landing outside that particular call's short window made a perfectly healthy host look offline for that cycle; observed in practice as "takes a long time to show online, then randomly shows offline" and matched by a firehose of `mdns_sd` query/response log lines (millions of lines captured in ~15s) consistent with constant daemon churn. New `Browser` type keeps one `ServiceDaemon` + `Receiver<ServiceEvent>` alive, draining into a cache on each `snapshot()` call (`ServiceResolved` inserts, `ServiceRemoved` evicts) — once a host is seen it stays known until a real removal event says otherwise. `discover_hosts` now lazily builds one `Browser` behind a `static OnceLock` and returns the live cache (with a short grace sleep only when the cache is still empty), instead of cold-restarting every poll. `browse()` itself is untouched (still used by `devtools/hostdisc.rs`'s one-shot CLI lookup, where cold-start-per-call is the correct behavior).
